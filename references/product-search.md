# 商品搜索与两阶段推荐

本参考只用于首次搜索、推荐和搜索结果的多轮条件更新。查看候选详情、编号回查、商品比较或链接研究时改读 `product-followups.md`。正常推荐严格执行 search → prepare → finalize；模型做语义选择和取舍，脚本做来源校验、排序、事实绑定和最终 Markdown。

## 1. 搜索前门槛

### 医疗安全

用户描述当前面部过敏红肿、明显肿胀、持续或严重瘙痒/灼痛、皮疹/荨麻疹、水疱/渗液、眼周或口唇肿胀、疑似感染，或要求用化妆品治疗湿疹、皮炎、严重痤疮时，不调用任何搜索、比较或交易命令。以下三段是完整回复，逐字使用后结束：

```text
你描述的面部过敏、红肿或肿胀属于需要专业判断的健康问题。为避免进一步刺激，我不能根据这些症状为你搜索或推荐化妆品，也不建议自行依靠化妆品处理。

请暂停使用疑似引发反应的新产品，并尽快咨询皮肤科或其他合适的医疗专业人员。

如果同时出现呼吸困难、喉咙发紧、吞咽困难、舌头或喉咙肿胀、明显头晕或晕厥，请立即联系当地急救服务。
```

仅描述“敏感肌”、预防刺激或寻找温和产品，没有当前异常症状时继续普通购物流程，不作治疗承诺。

### 单问题澄清

- 已有具体商品、品牌片段或品类，并至少有一个预算、功效、规格、人群或场景约束：立即搜索。
- 只有模糊意图而无商品或品类：只问最能缩小范围的一个问题。
- 已有宽泛品类，但唯一偏好只是“舒服/好用/合适”：只问一个二选一问题，例如“你说的肤感舒服更偏向清爽不黏，还是滋润舒缓？”
- “油皮/干皮/敏感肌”、预算、功效和场景不是品类，不得自行猜测。
- 明确要求今天、明天或具体日期前送达却没有地区：只回复“请问收货地区是哪里？”。
- 每轮最多一个问题，不重复询问已有信息。

## 2. 搜索

把用户当前完整需求原样保留在查询中，只执行一次：

```bash
node "<Skill 返回的 Base directory>/scripts/filtalgo.js" search "<完整用户需求>" --request-profile-stdin --json --agent-response <<'FILTMALL_PROFILE'
{"request_profile":{"category":"保湿面膜","audience":"干性皮肤","needs":["补水","保湿"],"budget":{"currency":"CNY","max":100}}}
FILTMALL_PROFILE
```

- `texture_preference` 只写清爽、滋润、黏腻、轻薄等真实肤感。预算上限不等于价格优先；只有用户明确说“预算优先/价格优先/低价优先”时才写 `selection_priority: "价格优先"`。不使用含义混淆的 `preference`。
- 不先缩成品类词，不执行 `search-spu`、`search-tools`、`config reset`，不为补字段或排版重跑搜索。
- 脚本路径逐字使用宿主返回的绝对 Base directory；不得把 `${CODEBUDDY_SKILL_DIR}` 当作 Shell 变量。
- 不追加管道、`head`、`tail`、Python、PowerShell，不写临时文件。
- 无结果时，将结果中 `response.markdown` 从第一个 `#` 开始逐字作为唯一最终回复后结束。
- 有候选时，只根据返回的 `model_task` 生成 JSON，然后执行返回的 `prepare_command`。工具轮直接调用命令，不先输出英文计划或商品分析。

## 3. 第一阶段：prepare

search 的 `model_task.selection_priority` 是脚本根据用户原话确定的权威结果。不得把“100 元以内”自行扩写为“价格首要”。

按 `output_schema` 生成：

- `needs_focus`：只概括用户真实说过的需求和取舍。
- `candidates`：从本次全部搜索候选中选择任意有展示价值的子集；不新增、重复或改写 `spu_id`。用户指定数量时尽量满足；未指定时自主决定，不设固定默认条数或全局最大条数。
- 每款的 `product_overview`、`score`（1.0–5.0）和完整 `dimension_results`。只用该候选自己的名称、规格和属性；不从成分推导未标注功效。综合分使用的每个维度都必须展示，证据不足写“暂时无法确认”。
- 候选事实没有提供品牌口碑、知名度、认可度、销量或市场排名；不对这些项目数值评分，不在概览或理由中下结论。脚本会将无原始证据的口碑类维度改为“暂时无法确认”，并移除相应文案。
- 只有 `selection_priority.price_first=true` 时，价格才必须作为主要维度并实际影响分数、候选和排序。
- 品牌概述由脚本根据已审核本地知识自动绑定；本阶段不生成品牌文案。

将单个 JSON 通过 heredoc 交给 `prepare_command`。prepare 只校验来源、去重、硬预算和分数，按综合分降序、同分沿用搜索顺序，不使用固定词表重新评分。

## 4. 第二阶段：finalize

prepare 只返回已排序候选的第二阶段 `model_task`，不再返回模型不消费的完整草稿。按 `output_schema` 只生成：

- 每款候选的 `recommendation_reason`；
- 排名第一且评分不低于 3.5 时的 `primary_choice`，否则使用 `no_primary_reason`；
- 只在有真实差异时提交 `alternative_choices`。

不得增删候选、重新评分、改变维度或排序，不得生成 Markdown、价格、规格和链接。将单个 JSON 通过 heredoc 交给 `finalize_command`。

- prepare 或 finalize 失败时最多根据错误修正当前 JSON 一次，不得重新搜索。
- finalize 成功后，下一条 assistant 消息的第一个字符必须是 `response.markdown` 的第一个 `#`，然后逐字输出完整 Markdown。不添加英文前缀、解释、摘要或收尾。
- `response.products` 和 `card_order` 已与文字同序绑定；不重新排序或换图、换价、换规格、换链接。

## 5. 多轮条件更新

在当前会话中维护一条“当前完整需求”，只使用用户原话：

- 新增条件：与仍有效条件合并。
- 覆盖条件：同一维度只保留最新值。
- 取消条件：从完整需求中删除。
- 更换品类：删除旧品类专属条件。

用户新增、覆盖、取消任何条件，或说明新的优先级，都必须把合并后的完整需求重新执行第 2–4 节，不得直接确认旧结果。例如首轮“预算 100 元以内”后再说“预算优先，效果够用就行”，是优先级变化，必须重新搜索、评分和排序。

每次新结果替换最近一次可见候选编号和 SKU 身份。硬条件不满足的商品不展示；证据未知也不当作满足。

## 6. 固定输出与错误

脚本固定生成 `### 我理解你的需求` → `### 你的需求重点` → `### 候选商品` → 每件商品独立纵向分段 → `### 如果只买一款` 或 `### 当前没有合适的首选` → 有真实次选时的 `### 其他情况可以这样选`。候选引导语只在 `### 候选商品` 下出现一次，禁止横向 Markdown 表格。每款的图片、名称、当前价格、推荐规格、H5 链接、编号、文字顺序和卡片必须同元组。

价格优势只在当前价、同款同规格对比价、平台、节省金额/比例、采集时间和来源链接完整时展示；有多条时选最高有效对比价。至少一个候选有价格优势时，全文末端只显示一次价格波动提示。

无结果时说明当前条件没有形成合格候选，只问是否愿意放宽一个最关键条件；不列商品或首选。命令失败时去技术化说明，不暴露命令、CLI、字段、参数、内部 ID、堆栈或服务细节。
