# 会员授权、下单确认与支付边界

访客身份仅用于连接 Control 会话与公开查询，**不等于商城会员授权**。涉及购物车、收货地址、优惠券、结算、订单、物流、售后与部分客服场景时，按本参考处理授权与交易确认。

## 会员授权与恢复原任务

1. **展示真实授权链接并结束本轮**：当服务返回 `status="authorization_required"` 或携带 `authorization_url` 时，以“前往授权”等 Markdown 可点击文字展示该验证链接，目标完整保留返回值，不显示原始 URL。说明完成登录授权后告知即可继续，本轮立即结束，不轮询刷屏、不改写链接参数。
2. **同一会话 `resume` 恢复**：用户表示已完成授权后，必须沿用**同一 `conversation`** 调用 `resume`：
   ```json
   {"op":"resume","conversation":"<同一对话标识>"}
   ```
   服务会自动完成设备授权核验并继续此前因授权暂停的业务请求，**不要把原业务问题重新 `send` 一遍**。
3. **未完成授权与轮询间隔**：若用户尚未完成验证，`resume` 仍返回 `authorization_required` 与原 `authorization_url`；遵守轮询间隔，继续展示原链接，不要新建第二个授权请求。
4. **待恢复拦截（`RESUME_REQUIRED`）**：当授权或授权后继续请求尚未结算时，新的 `send` 会返回 `RESUME_REQUIRED` 且新消息不会提交。宿主必须保留用户刚发的新消息，先通过 `resume` 处理完原任务并确认终态后，再根据用户意图决定是否发送新消息；`force` 与 `wait:false` 均不绕过该保护。
5. **授权异常与放弃（`auth-reset`）**：遇到 `AUTHORIZATION_UNCERTAIN` 等暂时无法确认状态时，保留本地状态稍后重试 `resume`。只有用户**明确表示拒绝授权或放弃本次操作**时，才执行：
   ```json
   {"op":"auth-reset","conversation":"<同一对话标识>"}
   ```
   `auth-reset` 仅清理本地待授权记录，不会撤销远端已生效的授权；若 `AUTHORIZATION_EXPIRED` 提示授权已过期，再按用户意图重新发起业务请求。

## 解除授权与退出本机身份

- **解除当前商城会员授权**：仅在用户明确要求解除/撤销筛电商城授权时执行：
  ```json
  {"op":"revoke-authorization","conversation":"<同一对话标识>"}
  ```
  远端权威撤销成功后客户端才清理本地 `delegation_id` 引用；无已完成授权时返回 `NO_DELEGATION`。
- **退出本机访客/平台身份**：仅在用户明确要求退出本机身份时执行：
  ```json
  {"op":"logout","conversation":"<同一对话标识>"}
  ```
  若仍有未结算请求须先核对终态；退出本机身份不会撤回已产生的订单或其他设备的会话。

## 下单预览、确认与支付链接

- **写操作必须先确认**：修改购物车、创建/修改/删除地址、创建订单、取消订单或提交售后前，先把具体商品、规格、数量、收货地址、商品金额、运费、优惠、应付总额或操作影响清楚列给用户，**收到当前对话的明确确认后才提交执行**。提交订单时不得顺带勾选购物车里用户未确认的其他商品；若预览改动了购物车状态需主动说明。
- **结果不明严禁盲目重试**：下单或写操作遇到超时、断线或未知态时，先走 `resume` 及订单/支付状态查询核实，不断言“未创建订单”或“未扣款”，不自动重发写请求。
- **首轮给出真实收银台链接**：订单提交或支付准备成功后，同一轮回复必须给出应付金额、当前支付状态（如“待付款”）及真实支付入口：
  - 优先展示响应中的结构化 `payment_links`（客户端已将已知 buyer `/payment/cashier` 安全映射至同环境移动端 H5 `/pages/mine/payment/payOrder`）；
  - 若订单已创建但本轮 `payment_links` 为空，沿用同一 `conversation` 追问一次支付链接（如“为订单 `<订单号>` 拉起支付并返回支付链接”），拿到后以“前往收银台”等 Markdown 文字链接展示，目标保持原值，不显示原始 URL；仍无结果则如实说明，绝不自行构造链接或二维码。
- **付款完成判定**：付款由用户在真实收银台页面自行完成。展示支付链接或完成结算创建均不代表已付款；只有后续查询拿到明确已支付业务状态时，才能表述为已付款。
